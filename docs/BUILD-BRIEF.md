# Vero Scan web product: build brief

Everyone working on this repo follows this document. Sources of truth: `docs/design/*.dc.html` (approved screens, with `vero.css`, `vero-ui.js`, `vero-3d.js`), `docs/knowledge/vero-scan-milestone-1-plan.md` (architecture, schema, scoring), `docs/knowledge/vero-scan-*-rule-pack-map.md` (requirements per country), `docs/knowledge/vero-scan-verification-solutions.md` (how each fact is verified), `docs/knowledge/vero-product-document.txt` (the Client's product document).

## Scope of this version
Web product only. MVP countries are **Delaware (US-DE), United Kingdom (GB), Nigeria (NG)** and nothing else. Investor pages and the mobile app come later. No live API keys exist yet: everything must run and be fully testable without them, and each integration switches on when its key is set.

## Honesty rules (non-negotiable)
- Never present sample data as real. Fixture connectors run only when `CONNECTOR_MODE=fixture` and are refused when `NODE_ENV=production`. In production a connector with no key returns `status: "unavailable"`, which the UI shows as the "one source is down" state and which does not count for or against the score.
- A source that needs a number only the company can give (VAT, ICO, US trademark serials) returns `status: "unsupported"` with a plain reason, and a paid vendor still preparing its report returns `status: "waiting"`. Like "unavailable", neither counts for or against the score: the rules that need them show as "to check" with that reason. Never guess an identifier. Scans run in two stages so identifiers found by the registers reach the sources that need them; see `docs/ENGINE-STATUS.md`.
- Paid vendors (Middesk, Cobalt, Mono) keep the vendor's own reference per company and reuse a good answer for `VENDOR_CACHE_DAYS` (default 30). "Check again" refreshes it. Errors are never cached.
- The ICO, NDPC and sanctions sources read stored copies of their lists (`reference_data`, kept by the `reference.refresh` job, off until `REFERENCE_REFRESH_ENABLED=true`). Every answer says "List last updated on {date}". A copy past its freshness limit (`REFERENCE_MAX_AGE_HOURS`, sanctions `REFERENCE_SANCTIONS_MAX_AGE_HOURS`) is `unavailable`, never an answer: a stale sanctions list never says "no match". A failed, empty or under-half-size download never replaces a good copy.
- Scale monitoring (`monitoring.rescan-due`, off until `MONITORING_ENABLED=true`) re-scans weekly through the normal pipeline with trigger `monitoring`, reuses paid vendors' kept answers, and is capped per organisation and overall per day. It notifies only meaningful changes (new urgent or important issue, status change, sanctions match, score drop of 5 or more with a new issue). "Could not be checked" is never a change. See `docs/ENGINE-STATUS.md`.
- `CONNECTOR_RECORD_DIR` saves live provider responses, with secrets and personal data removed, for checking parsers (`docs/RECORDING-REAL-RESPONSES.md`). Like fixture mode it is refused when `NODE_ENV=production`.
- "Not found" is never presented as proof of absence. Every fact stores its source, retrieval date and verification tier. The UI says how we know in plain words.
- Delaware: never scrape; status comes from a licensed vendor or an uploaded Certificate of Good Standing validated by the user, and the UI says "Certified {date}", never a live status.
- Not legal advice. Rule content ships as `status: draft` until Code & Clause approves it; nothing in the code marks a pack approved by itself.
- The GitHub connection (a read-only GitHub App, off until registered) reads repository metadata and only an allowlist of 27 file paths, enforced in code before any request. What it reads is evidence a person confirms: tier 4, never a verified badge, never a statement that a licence is compliant. Its files reach the vault through the same path as uploads and still need a person to confirm them. A repository that couldn't be read is "not checked yet". See `docs/ENGINE-STATUS.md` and `docs/CONNECT-GITHUB.md`.
- Never log document content, secrets or tokens.

## Stack (from the plan)
- npm workspaces monorepo: `apps/web`, `apps/api`, `apps/worker`, `packages/shared`, `packages/rules`, `packages/connectors`. TypeScript strict everywhere. Node 24.
- Web: Next.js (App Router) + React. Styling: port `docs/design/vero.css` as the global stylesheet rather than Tailwind, since it is the approved design system. `images.unoptimized: true` and `sharp` must not be installed (LGPL).
- API: Fastify + zod. Modular monolith: one folder per module (`auth`, `organisations`, `companies`, `questionnaire`, `scans`, `vault`, `reports`, `review`, `deadlines`, `notifications`, `orders`, `admin`, `audit`).
- Database: PostgreSQL with Drizzle ORM and plain SQL migrations. Every tenant table has `organisation_id` and a row-level security policy. The API connects as a non-superuser role and sets `app.organisation_id` per transaction.
- Local database: `embedded-postgres` (real Postgres via npm, no Docker). `npm run db:start`.
- Jobs: a `JobQueue` interface. `InProcessQueue` for development and tests; `BullMQQueue` on Valkey when `VALKEY_URL` is set. Never Redis 7.4+.
- Files: a `FileStore` interface. Local encrypted-at-rest disk in development; S3-compatible (DigitalOcean Spaces) when `SPACES_*` is set. Signed short-lived URLs only.
- Email: a `Mailer` interface. In development it writes to an `outbox` table and logs the link; Resend when `RESEND_API_KEY` is set.
- Document AI: a `Classifier` interface. Heuristic classifier (filename and text keywords, text via `pdfjs-dist`) by default. The Claude document helper (`ClaudeDocumentHelper`, official `@anthropic-ai/sdk`) is used for an organisation only when `AI_DOCUMENT_HELPER_ENABLED=true`, `ANTHROPIC_API_KEY` is set and the organisation has switched it on (`organisation_setting`, migration 0013, off by default). It reads PDFs as documents (so scanned pages are read too), images as images, and suggests a slot, a few fields with quoted evidence and plain concerns, through structured output. Any failure falls back to the heuristic, marked "needs a person". Always confirmed by the user; AI never judges authenticity or sufficiency.
- Tests: Vitest for units and API integration against real embedded Postgres; Playwright for end-to-end.
- Licences: no GPL, AGPL, LGPL or SSPL dependencies. Banned: Poppler, Ghostscript, MuPDF, Redis 8, node-canvas, sharp. `npm run licences` fails on them.

## Authentication
Email magic link (design: "no password to remember"), 15-minute single-use token, stored hashed. Sessions: opaque random token in an `HttpOnly; SameSite=Lax; Secure` cookie, stored hashed, rolling 30-day expiry, revocable. No Google or other social sign-in in this version (owner's decision, 5 Nov 2026): leave out the "Continue with Google" button shown in the SignIn designs. Optional TOTP MFA. Rate limits on sign-in by IP and email. Origin check on state-changing requests. Roles: `owner`, `member`, `lawyer`, `admin`. Account deletion is real. Every security-relevant event writes `audit_log`.

## Data model
As in plan section 7, plus `session`, `magic_link`, `outbox`, `notification`, `document_order`, `lawyer_booking`, `deadline`, `reference_data` (shared reference table, written only through system-scope functions) `monitoring_change` (tenant table), `github_installation` and `github_repository` (tenant tables, migration 0014, no tokens stored) and `organisation_setting` (tenant table: the organisation's own switches, such as the document helper, all off by default). A signed-up user gets one organisation; an organisation has one or more companies (one per legal entity, for example Delaware parent and UK and Nigerian subsidiaries).

## Scoring (plan 11.5, proposals pending Client approval, so keep them in one config file)
Outcomes: pass, gap, defect, verify, not_applicable. Severity weights: critical 10, high 6, medium 3, low 1. Layer score = 100 x passed weight / applicable scored weight; verify and not_applicable are excluded. Overall = weighted mean: Corporate 20, IP 20, Compliance 20, Commercial 15, Fundraising 10, AI and data 15 (redistribute if a layer has no applicable rules). A layer earns its full weight once its scored checks add up to 15 in severity weights; below that its weight shrinks in proportion and the rest goes to the other layers, so one small check can't carry a whole layer (owner's decision, 6 Nov 2026). An open critical finding caps its layer at 49, and while any scored critical finding is open the overall score can't exceed 74, so the word can't be Healthy; a free range's top is cut to match. An empty document slot stays "not checked yet" on every plan and never lowers a score: it becomes a gap only when the person says they don't have that document, or answers no to a question about it. Every score says what it rests on: counted is scored findings with pass, gap or defect, total adds verify, and not_applicable is left out ("Based on 16 of 118 checks"). A free range counts what it used, out of every check that applies, so a thin read looks thin. Groups sum across companies. Status words: 75 or more Healthy, 50 to 74 Needs work, under 50 At risk. Healthy waits for evidence: while under half of the applicable checks count, a score of 75 or more says "Early read" instead (owner's decision, 6 Nov 2026), on the overall score and on each area. The other words don't wait. Free plan shows a range. Verified badge needs a score of at least 80 (configurable), at least half of the applicable checks counted (owner's decision, 6 Nov 2026), no open critical findings and a lawyer review in the last 12 months. Priority = severity x cost-of-delay factor (deadline proximity, penalty, fundraising relevance); show top 5. Every snapshot records method and rule-pack versions. "Points" for a fix = how much the overall score rises if that finding alone passed, calculated, never hard-coded.

## Plain-language rules for anything users read
Layer names in the UI: Company foundations, Intellectual property, Compliance, Contracts, Fundraising, AI and data. Severity words: Urgent (critical), Important (high), Worth doing (medium, low). Verification tiers are never shown as "Tier N"; show "Checked with Companies House today", "From our licensed data provider", "Found on the NDPC list", "You uploaded this and we read it", "You told us", "A lawyer read this". Every finding has: what is missing, why it matters, what happens if left, and the fix.

## Quality bar
TypeScript strict with no `any` in new code. Input validated with zod at every boundary. Each module ships with tests covering success, failure, permissions and tenant isolation. Errors return `{ error: { code, message } }` with plain messages. Empty, loading and error states are part of every screen. Accessibility: WCAG 2.2 AA, real controls, visible focus, reduced motion respected. No secrets in code; `.env.example` lists every variable. Do not commit: the owner decides when to commit.

## Lint
`npm run lint` is still the one command, still `--max-warnings 0`, same `eslint.config.mjs` and the same rules (nothing ignored, nothing weakened). It now runs `scripts/lint.mjs`, which runs ESLint once per workspace (`apps/api`, `apps/web`, `apps/worker`, each `packages/*`) and once for everything left over, each in its own Node process one after the other. Extra arguments pass through (`npm run lint -- --fix`), and every pass runs even if an earlier one fails, so one run shows every problem.

Why: the type-aware rules build one TypeScript program per tsconfig, and a single `eslint .` kept all seven in memory at once (about 2.0 to 2.2 GB, and 4 to 5 minutes on the 8 GB machine; it died out of memory when the machine was short of RAM). The API source and its dependencies are read three times, because the worker and the root scripts import the API. The cause is the number of programs, not `@anthropic-ai/sdk`: a program that imports only the SDK is 431 files, about 110 MB and 0.3 s to check, a tenth of the API program. Separate processes free each program before the next starts, so the peak is the largest single workspace (about 1.1 to 1.3 GB, the API) and the run is about 15 percent faster. Checked against the old single run on the same source: the same 6 messages, and a deliberate violation (`any`, `==`, floating promise, restricted `pg` import and others) in each workspace still fails its pass.

Not done: sharing one program between the API, worker and scripts (they have identical compiler options) would save roughly another 35 seconds and 600 MB, but needs a small change to `eslint.config.mjs`, which the config-protection hook blocks. A shared ESLint `--cache` is not used on purpose: cached results for type-aware rules can go stale when a different file's types change.
